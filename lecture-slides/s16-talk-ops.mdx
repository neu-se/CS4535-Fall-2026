## Pawtograder Wasn't Losing Them

<div style={{fontSize: '0.58em', textAlign: 'left', marginTop: '0.4em'}}>

<div style={{backgroundColor: 'rgba(100,150,255,0.12)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**240** student repositories. **13** students had pushed. **44** student pushes reached Pawtograder, and **every one** was recorded.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**43 of the 44** were **rejected**, each with the same message: *"it is identical to the assignment's starter code."* **40** of those were real work.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px'}}>

One rejected push was a 10-file change. And one student the staff named as "working" had a submission with **no files at all**: someone had clicked "make active" on a rejected row.

</div>

</div>

<aside className="notes">
**The report said "not recording." The first query said otherwise.** The submissions table had a row for every push. What the report called "nothing" was a row marked inactive, with an error attached, that the dashboard showed as not submitted.

**Say what this means about reports in general.** A user describes the symptom they can see. "Not recording" was a reasonable reading of the dashboard, and it was wrong about the cause. Triage starts by checking the claim, not by accepting it.

**The third box is worth one sentence.** The staff had named two students as "confirmed working." One had a real accepted submission. The other had a rejected, fileless row that the student and then a grader had manually made active. The dashboard said "submitted"; there was no code behind it. Evidence from a user can be wrong in both directions.

**Why the rows existed at all is the first software decision in this story.** An earlier version of this code deleted a rejected push. Somebody changed it to keep the row and attach the reason, because deleting it made the failure invisible to the student. That change is why this investigation took an afternoon rather than a week.

**The counts are as of Tuesday afternoon, and they are student pushes only.** Course staff had also pushed seven test commits, and those went through, because staff pushing to their own repository are exempt from the empty check. That exemption is part of why the staff saw it working. Three of the 43 rejections really were empty (one added only a `.env` file, one only a `test.txt`), which is why 40 were real work. If anyone asks why 240 repositories and only 13 students: the assignment was a week from its deadline.

> **Transition:** So why would a 10-file change look identical to the starter code?
</aside>

</Slide>

## One File Nobody Edited

<div style={{fontSize: '0.56em', textAlign: 'left', marginTop: '0.3em'}}>

The assignment's `pawtograder.yml`, in the course's grader repository:

</div>

```yaml
submissionFiles:
  files:
    # The default is to submit all java, arr, md, and python files.
    # You should almost definitely change this.
    - '**/*.java'
    - '**/*.arr'
    - '**/*.py'
    - '**/*.md'
```

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.4em'}}>

The project is **TypeScript**. Pawtograder decides "empty" by comparing only the files these patterns match against the starter code. In the starter code, that's **one file: `README.md`**.

</div>

<p className="fragment" style={{fontSize: '0.58em', marginTop: '0.5em', fontWeight: 'bold', color: '#e76f51'}}>
Any push that didn't touch a Markdown file looked identical. The one student who added a .md file got through.
</p>

<aside className="notes">
**Let the comment in the file do the work.** Read "You should almost definitely change this" out loud and pause. The template shipped a warning, in a file nobody had a reason to open after the assignment was created.

**Explain the check in plain terms for the mixed room.** For an assignment that doesn't allow empty submissions, Pawtograder hashes the student's files and compares the result with a hash of the starter code. It only looks at the files the patterns select, so that a changed lockfile or a stray build output doesn't count as work. If the patterns select the wrong files, the comparison is between two things that were never going to differ.

**Whose fault is it?** Nobody's, and say that. The template default was reasonable for the Java and Python courses it was written for, the staff had turned the autograder off and had no reason to open the file, and the platform did exactly what the config said. It's a systems failure: a default that is safe in one context and silently wrong in another, with no signal when it goes wrong. That framing is what a blameless postmortem looks like, and Arc 4 names it.

**The fix was one commit to this file.** New pushes were accepted within a minute. The rejected ones were not, and recovering them comes up in Arc 4.

> **Transition:** Let's go back to your board. Which of your columns answered this?
</aside>

## Who Answered Each Question?

<div style={{fontSize: '0.42em', textAlign: 'left', marginTop: '0.2em'}}>

| Question | Where the answer lived | What put it there |
|---|---|---|
| Can I look without breaking anything? | A **read-only replica** of the database, and a narrowly scoped cluster login | Infrastructure decision |
| Were the pushes recorded? | Submission rows, **kept on purpose** when rejected | Software decision |
| Why were they rejected? | An error row with a machine-readable type: `empty_submission` | Software decision |
| What was it comparing? | The config, copied into the database, and the stored hash of each starter file | Software decision |
| Which code was running? | The **image tag pinned** in the deploy config, which names one commit | Infrastructure decision |
| Who made the empty row "active"? | An **audit table** of every change, with who made it | Software decision |
| Did any pushes go missing? | **GitHub's** record of pushes, compared with ours | Outside: our logs were gone |

</div>

<p className="fragment" style={{fontSize: '0.56em', marginTop: '0.45em', fontWeight: 'bold', color: '#e76f51'}}>
Almost every answer was in the database, because someone designed it to be there.
</p>

<aside className="notes">
**Point at the whiteboard for each row.** "Database" column: rows 2, 3, 4 and 6. "Code and config": row 5. "GitHub": row 7. "Logs": nothing. "Dashboards": nothing. Say the count, and compare it with what the room predicted in the warm-up.

**Explain the two infrastructure rows in one sentence each.** A **replica** is a live, read-only copy of the database; you can run any query against it with no risk of changing a student's grade. The cluster login let me read pods and connect to the database, and nothing else, because it was written that way. Both are decisions someone made months ago so that an investigation like this one could be safe.

**Row 7 is the interesting one.** To check that no pushes had been dropped on the way in, I needed a record of every push. Pawtograder's own logs keep about two hours. GitHub keeps pushes indefinitely. So the only trustworthy answer came from outside our system.

**This is the thesis; say it plainly.** Whether you can answer "what happened?" was decided long before Tuesday, by people choosing to keep a rejected row, record an error type, keep an audit trail, and pin an image tag. None of those were built for this incident.

## What Didn't Help

<div style={{fontSize: '0.56em', textAlign: 'left', marginTop: '0.4em'}}>

<div style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**Logs.** Pawtograder keeps a pod's logs for about **two hours**. The first rejection was **six days** earlier.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**Alerts.** Production has **37** alert rules. None of them are about rejected submissions.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px'}}>

**Detection.** The first thing that noticed was **a person, six days in**, writing an email.

</div>

</div>

<aside className="notes">
**Each of these is a decision, not bad luck.** Logs are kept briefly because nobody has set up somewhere to send them yet. Alerts cover what someone thought to write an alert for, and so far that's mostly infrastructure: the database, queues, memory, backups. Detection by a user is what's left when the first two don't cover a failure.

**Six days matters in human terms.** A student who pushed on day one and saw "not submitted" for six days was probably worried, pushed again, or emailed a TA. Every day between the failure and the detection costs somebody something.

**Hold the alert line.** In Arc 3 you'll show that the number that would have caught this was already being collected. That's the pivot of the session.

<Slide>

## Infrastructure as Code

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.55em', borderRadius: '8px', fontSize: '0.56em', textAlign: 'left', marginTop: '0.3em'}}>

**Definition.** **Infrastructure as code (IaC)** means the servers, containers, networks and settings a system runs on are **described in files under version control**, and a tool makes the running system match those files. You change the system by changing a file, not by clicking in a console.

</div>

<div style={{display: 'grid', gridTemplateColumns: '1fr 1fr', gap: '0.5em', fontSize: '0.5em', textAlign: 'left', marginTop: '0.5em'}}>

<div style={{backgroundColor: 'rgba(42,157,143,0.12)', padding: '0.5em', borderRadius: '8px'}}>

**In Pawtograder**

- A **Helm chart** (a template for Kubernetes resources) plus one values file per environment, such as `values-prod.yaml`
- Kubernetes itself: every service is a file describing what should run
- `pawtograder.yml` per assignment: **configuration as code**, the same idea for app settings

</div>

<div style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px'}}>

**What it buys you**

- **Review.** A change to production is a pull request
- **Reproduce.** Staging and previews come from the same files
- **Answer.** "What is running?" has a written answer

</div>

</div>

<aside className="notes">
**Take this slowly; it's the first new term for half the room.** The contrast is the useful part: the alternative to IaC is a person logging into a server or a web console and changing a setting by hand. That works, once, and then nobody can tell what was changed, when, or why, and nobody can build a second copy.

**Name the tools only as examples.** Terraform, Pulumi and CloudFormation describe cloud resources. Helm and Kubernetes manifests describe what runs in a cluster. Ansible describes the configuration of machines. The Workspaces team will meet several of these in their own namespace this month.

**Configuration as code is the same idea one level up.** The file from Arc 1 is configuration as code: the grader settings for an assignment live in a git repository, and a webhook copies them into the database when you push. The fix for the incident was a commit, which means it was reviewable and it's in the history.

**The third "buys" is today's point.** In the investigation, "which version of the code was running?" had an exact answer because of this. Next slide.

> **Transition:** Here's what that answer looked like.
</aside>

</Slide>

## Which Code Was Running?

<div style={{fontSize: '0.56em', textAlign: 'left', marginTop: '0.3em'}}>

From `values-prod.yaml`, the file that describes production:

</div>

```yaml
edgeFunctions:
  image:
    tag: "main-20260927-38db5c7b"
```

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.4em'}}>

`38db5c7b` is a **commit**. I read the exact code that rejected those pushes, not the code on `main` today.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', fontSize: '0.54em', textAlign: 'left', marginTop: '0.4em'}}>

The alternative is `tag: latest`, which means "whatever was newest when this pod last started." Then nobody can say which code is running.

</div>

<aside className="notes">
**One minute.** The point is small and concrete: a pinned version turns "what's running?" from a guess into a lookup.

**Say why `main` today would have been wrong.** Code changes daily. If I had read today's version of the webhook, I might have found a fix that wasn't deployed, or a bug that wasn't there yet. The tag let me read the exact file that ran when those pushes arrived.

**Tie back to s06 in one line.** Sentry tags every error with the release, the commit SHA, for the same reason.

**Cut this slide first if you're over time.** Say "the deploy file names the exact commit that's running" during the IaC definition and skip to the reconcile loop.

> **Transition:** Writing it down is half. The other half is keeping reality in line with what you wrote.

## Declared vs. Running

<div style={{display: 'flex', alignItems: 'center', justifyContent: 'center', gap: '0.5em', fontSize: '0.52em', marginTop: '0.5em'}}>

**Definition.** **Configuration drift** is any difference between what's declared and what's running, or between two places that are supposed to say the same thing.

</div>

<aside className="notes">
**Draw this on the board next to the warm-up columns if you have room.** Three boxes, two arrows. It's the whole mental model of IaC.

**The reconciler is the part people forget.** A file on its own does nothing. Something has to read it and change the world to match: `helm upgrade` in a deploy, a Kubernetes controller that starts a new pod because the file says there should be three, or, in the incident, the webhook that copies `pawtograder.yml` into the database on every push. Kubernetes is built out of loops like this one, which is why a pod you delete by hand comes back.

**Drift is what happens when the loop doesn't close.** Someone changes the running system without changing the file, or the loop updates only part of what depends on the file, or the same fact is written in two places and only one gets updated.

> **Transition:** Three kinds, all from our own system.
</aside>

## Three Kinds of Drift

<div style={{fontSize: '0.5em', textAlign: 'left', marginTop: '0.3em'}}>

<div className="fragment" style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**Undeclared.** Something runs that no reconciler owns. The database access I used on Tuesday is a permission **an operator applied by hand**. It's written in a file, but no deploy applies it, and the cluster's management tool may quietly remove it.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**Duplicated.** The same fact lives in two places. Who may do what is checked in the **UI** (about 62 files) and again in **database policies** (about 1,300 calls). They've drifted apart: the UI lets you start things the database refuses.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px'}}>

**Stale.** Something derived from the declaration wasn't recomputed. After the config fix, Pawtograder re-hashed the **current** starter code, but not the older versions a student may have started from.

</div>

</div>

<aside className="notes">
**Reveal one at a time, about a minute each.**

**Undeclared.** This one is honest about our own shortcuts. To investigate, I needed to read the production database. That permission is a Kubernetes Role that an operator applied once, by hand. The file is in a repository, but no deploy applies it, and the file's own comment warns that Rancher, which manages the cluster, may reconcile it away. The day it disappears, the next investigation starts with a permissions ticket.

**Duplicated.** This is the Usability, Accessibility & Permissions team's project, and they should recognize it. The Ticket Hunt turned up the pattern in #983, #996 and #1010: the UI offers an action, you take it, and the backend refuses. That's two copies of the same rule that no longer agree. Ask: which copy is the truth? The database policy, because it's the one that is enforced. Paper Exams has a smaller version of the same thing: the region math exists once in the app and once in a Deno copy that has to be kept in sync by hand.

**Stale.** This came up in code review of the recovery script, the day after the incident. The config fix reseeded the starter-code hash for the latest version of the handout, but not for earlier versions. A student who started from an earlier version and changed nothing would then have looked like they did real work. It affected nobody this time, and the recovery script now recomputes all of them.

**The general lesson:** a declaration is only as good as the loop that enforces it, and the loop only covers what someone thought to include.

> **Transition:** Drift is how the running system gets away from what you wrote. Observability is how you'd notice.
</aside>

## Four Kinds of Telemetry

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.5em', borderRadius: '8px', fontSize: '0.52em', textAlign: 'left', marginTop: '0.2em'}}>

**Definition.** **Observability** is how well you can answer a *new* question about a running system from what it already records, without shipping new code. What it records is **telemetry**.

</div>

<div style={{fontSize: '0.44em', textAlign: 'left', marginTop: '0.4em'}}>

| | Answers | Pawtograder today |
|---|---|---|
| **Errors** | What broke, where, in which release, for whom | **Sentry → Bugsink**, every event tagged with the commit |
| **Logs** | What happened, line by line, in one process | Only what a pod still holds: **about two hours** |
| **Metrics** | How much, how often, how fast, over time | **Prometheus**, graphed in **Grafana**, with **37** alert rules |
| **Traces** | Where one request spent its time, across services | **Off** |

</div>

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.45em', borderRadius: '8px', fontSize: '0.5em', textAlign: 'left', marginTop: '0.4em'}}>

**Definition.** An **alert** is a rule over telemetry that notifies a person when it's true: "this number has been above that line for ten minutes."

</div>

<aside className="notes">
**Two definitions, and the first one needs care.** Observability is not a tool. It's a property of the system: can you answer a question you didn't plan for? Monitoring is the part you did plan for: the dashboards and alerts someone set up in advance. The incident was a question nobody planned for.

**Walk the table row by row, one sentence each, and connect each row to the incident.**
- Errors: they've seen Sentry in s06. A rejected submission isn't an exception, so nothing went to Sentry. The code was working as written.
- Logs: the most detailed record, and the one that disappears. With nowhere to send them (Loki, Elasticsearch, a cloud logging service), they vanish when the pod restarts or the buffer rolls over.
- Metrics: cheap, kept for weeks, and good for "is something changing?" They lose the details: a metric can tell you rejections went up; it can't tell you which student.
- Traces: off, because they cost storage and nobody has turned them on. s06 said this.

**Mention the database as a fifth source without adding a row.** Arc 1 showed most answers came from rows the software kept on purpose. That's telemetry too, in the widest sense, and it's the kind students will design into their own projects.

> **Transition:** Here's the metrics row, applied to Tuesday.
</aside>

## The Number Was Already There

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.3em'}}>

Pawtograder already publishes this metric, every minute, per course:

</div>

```
web_workflow_errors_recent{class_id="…", category="empty_submission", window="1h"}
```

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.4em'}}>

For **six days** it counted one course's pushes being rejected as empty. Of the 37 alert rules, **none** looks at it.

</div>

<p className="fragment" style={{fontSize: '0.58em', marginTop: '0.5em', fontWeight: 'bold', color: '#e76f51'}}>
Collecting a number is not the same as asking it a question.
</p>

<aside className="notes">
**This is the pivot of the session.** The room just learned that metrics exist and alerts exist. Here they are, both present, and not connected.

**If you have Grafana open, show it.** Explore, Prometheus, paste the metric name, filter to `category="empty_submission"`, and set the range to the last seven days. A real line is more persuasive than any slide. Check it before class: it is a one-hour window, so it shows bursts rather than a steady climb. If you don't have it open, the slide is enough.

**Explain the name for the mixed room.** Everything in the braces is a label: which course, what kind of error, over what window. One metric name, many time series, one per combination of labels. That's what lets one alert rule cover every course.

**Why wasn't there an alert?** Because an empty submission is usually normal: a student pushes before starting, sees the message, and pushes again. A rejection on its own isn't a problem. **Forty-three of 44 student pushes in one course** is. The alert isn't "any rejection"; it's "one course's rejections are far outside normal." They'll write it in Arc 4.

## What Will You Be Asked in November?

<div style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', fontSize: '0.5em', textAlign: 'left', marginTop: '0.2em'}}>

**8 minutes, as a team.** Write four lines in your team's channel:

1. **The email.** A user's report about your feature, in their words.
2. **The question.** What you'd need to know to answer it.
3. **Where the answer lives.** A row, a metric, an error, a log line. **Does it exist today?**

<aside className="notes">
**Teams sit together for this.** The prompts are a starting point; a team that writes a better email of its own should use it.

**Line 3 is where the thinking happens.** Most teams will first write "we'd check the logs." Push back with Tuesday's lesson: the logs are gone in two hours. Where does it live that you'd still have in a week? Often the honest answer is "nowhere yet", and that's a good outcome: it's a design decision they can make this month, while the feature is still on paper.

**What to listen for, per team. Don't hand these out; use them to nudge.**
- **Paper Exams.** The pipeline is asynchronous: upload, rasterize, OCR, match to the roster, grade. The email is about the match step. Signals: scans not matched to a student, per exam (a row they can count); the age of the oldest unprocessed batch in the queue (Pawtograder already alerts on queue age for other queues, `PawtograderQueueOldestMessageAging`); LLM provider errors and rate limits once they add bring-your-own-key grading. And one that is a correctness signal rather than a failure signal: how often a human overrides the LLM's suggested score. A sudden change means the model or the prompt changed underneath them.
- **Cloud Workspaces.** This is the IaC team: they own a namespace and will declare Forgejo and Coder in files. The email is about "ready." Issue #981 is already a status that says ready before the repo is usable, which is drift between a declared status and the running state. Signals: time from click to a usable workspace; a synthetic readiness probe (a robot that opens a workspace every few minutes and reports whether it worked); and, straight out of Tuesday, Forgejo webhook deliveries compared with the submissions they should produce.
- **Office Hours.** The email is about stale client state: the browser's copy of the queue stopped updating. Signals: realtime connections and reconnects per course (Pawtograder already alerts on realtime connection limits); the delay between a status change in the database and the client seeing it; time from raised hand to helped, as a distribution. That last one is the baseline the team already planned to measure, and it doubles as a product metric.
- **Usability & Permissions.** The email is the duplicated drift from Arc 2. Signals: permission denials from the database, counted by page and by role, are a live map of where the UI and the policies disagree. Accessibility has its own telemetry in CI: axe violations over time. And abandoned flows (started, never finished) are row E from s07.

## The Incident Loop

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.45em', borderRadius: '8px', fontSize: '0.5em', textAlign: 'left', marginTop: '0.2em'}}>

**Definition.** An **incident** is any unplanned event that stops users from doing what they came to do. **Incident response** is the loop below.

</div>

<div style={{fontSize: '0.44em', textAlign: 'left', marginTop: '0.4em'}}>

| Step | What it means | On Tuesday |
|---|---|---|
| **Detect** | Find out something is wrong | An email from course staff, **six days** after the first rejection |
| **Triage** | Find out what, how bad, and for whom | Read-only queries: 40 real pushes rejected, 11 students affected |
| **Mitigate** | Stop the harm from growing | **One commit** to `pawtograder.yml`. New pushes accepted |
| **Recover** | Repair the damage already done | A reviewed script restored all **40** and left the 3 truly empty ones alone |
| **Postmortem** | Write down what happened and what changes, **without blame** | This lecture, and a new alert |

</div>

<aside className="notes">
**Point at the board one last time.** The warm-up columns were all Triage. Most of the room jumped straight to "where would I look", which is right, and nobody asked how we'd have found out sooner, which is the Detect row.

**Two words need a sentence each.**

**Mitigate before recover, and they're different.** Mitigation stops the bleeding: after the config commit, no new student was harmed. Recovery repairs what already happened: the 40 rejected pushes were still rejected after the fix, and restoring them took a script. People under pressure try to do both at once, and that's where mistakes happen.

**This one had its mistakes, and they're worth admitting in class.** Code review of the recovery script caught three problems: the older starter-code versions that weren't re-hashed (the stale drift from Arc 2), a case where two separate database updates could briefly leave a student with no active submission and move their grading assignment, and a student's repository name in a commit message. None of them hurt anyone, because the script ran as a dry run first, then on one repository, then on the rest. That's the habit to copy: rehearse the recovery before you run it for real.

**Blameless means the question is "what let this happen", not "who did it."** Arc 1 already answered it that way: a reasonable default, a file with no reason to open, and no alert.

> **Transition:** So, the alert that should have existed. Write it with me.
</aside>

## Write the Alert That Should Have Existed

<div style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', fontSize: '0.54em', textAlign: 'left', marginTop: '0.3em'}}>

**2 minutes, whole room.** Using `web_workflow_errors_recent`: **when** should it fire, **who** gets it, and **what do they check first**?

</div>

<div className="fragment" style={{fontSize: '0.5em', textAlign: 'left', marginTop: '0.5em'}}>

```yaml
- alert: PawtograderEmptySubmissionSpike
  expr: web_workflow_errors_recent{category="empty_submission", window="1h"} > 10
  for: 30m
  annotations:
    summary: "Course {{ $labels.class_id }}: many pushes rejected as empty"
    runbook: "Check that course's submissionFiles in pawtograder.yml first"
```

</div>

<p className="fragment" style={{fontSize: '0.56em', marginTop: '0.4em', fontWeight: 'bold', color: '#e76f51'}}>
With a threshold tuned to this course's traffic, it fires on day one, not day six.
</p>

<aside className="notes">
**Take answers before revealing the rule.** Someone will say "alert on any rejection." Ask what happens on the first night of every assignment, when dozens of students push the untouched starter code to test their setup. The alert fires every night, and within a week everyone mutes it. An alert nobody acts on is the same mistake as a test nobody maintains, from s07.

**Then reveal and read it line by line.** `expr` is the condition. The number is a threshold you'd tune from history; ten per hour for one course is a starting guess. `for: 30m` means it has to stay true for half an hour, so one burst doesn't page anyone. The `runbook` line matters most: it tells the person who receives it what to check first, and here that's the file from Arc 1.

**Be honest that this is a sketch, and say why the fragment hedges.** This course's rejections mostly trickled in a few at a time across six days. The busiest hour had exactly ten, all from one student pushing repeatedly, so `> 10` would never have fired. A **rate** is the better rule: rejections divided by pushes, per course, over a day. Forty-three of 44 is a rate nobody could miss. Say that, because the gap between "the obvious rule" and "the rule that fires" is exactly what they'll be graded on in Game Day 2. Before class, confirm the `window` label's value in Grafana; the rule is written against `1h`.

**Connect forward.** Game Day 1 on Thursday is the first time they'll run this loop themselves, with the response narrated. Game Day 2 on Nov 5 is "write the alert that should have existed", against a fault injected into their own demo class. Today was the rehearsal.
