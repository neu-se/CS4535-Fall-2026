## Pawtograder Wasn't Losing Them

<div style={{fontSize: '0.58em', textAlign: 'left', marginTop: '0.4em'}}>

<div style={{backgroundColor: 'rgba(100,150,255,0.12)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**240** student repositories. **13** students had pushed. **44** student pushes reached Pawtograder, and **every one** was recorded.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', marginBottom: '0.4em'}}>

**43 of the 44** were **rejected**, each with the same message: *"it is identical to the assignment's starter code."* **40** of those were real work.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px'}}>

One rejected push was a 10-file change. And one student the staff named as "working" had a submission with **no files at all**: someone had clicked "make active" on a rejected row.

</div>

</div>

<aside className="notes">
**The report said "not recording." The first query said otherwise.** The submissions table had a row for every push. What the report called "nothing" was a row marked inactive, with an error attached, that the dashboard showed as not submitted.

**Say what this means about reports in general.** A user describes the symptom they can see. "Not recording" was a reasonable reading of the dashboard, and it was wrong about the cause. Triage starts by checking the claim, not by accepting it.

**The third box is worth one sentence.** The staff had named two students as "confirmed working." One had a real accepted submission. The other had a rejected, fileless row that the student and then a grader had manually made active. The dashboard said "submitted"; there was no code behind it. Evidence from a user can be wrong in both directions.

**Why the rows existed at all is the first software decision in this story.** An earlier version of this code deleted a rejected push. Somebody changed it to keep the row and attach the reason, because deleting it made the failure invisible to the student. That change is why this investigation took an afternoon rather than a week.

**The counts are as of Tuesday afternoon, and they are student pushes only.** Course staff had also pushed seven test commits, and those went through, because staff pushing to their own repository are exempt from the empty check. That exemption is part of why the staff saw it working. Three of the 43 rejections really were empty (one added only a `.env` file, one only a `test.txt`), which is why 40 were real work. If anyone asks why 240 repositories and only 13 students: the assignment was a week from its deadline.

> **Transition:** So why would a 10-file change look identical to the starter code?

<Slide>

## One File Nobody Edited

<div style={{fontSize: '0.56em', textAlign: 'left', marginTop: '0.3em'}}>

The assignment's `pawtograder.yml`, in the course's grader repository:

</div>

```yaml
submissionFiles:
  files:
    # The default is to submit all java, arr, md, and python files.
    # You should almost definitely change this.
    - '**/*.java'
    - '**/*.arr'
    - '**/*.py'
    - '**/*.md'
```

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.4em'}}>

The project is **TypeScript**. Pawtograder decides "empty" by comparing only the files these patterns match against the starter code. In the starter code, that's **one file: `README.md`**.

</div>

<p className="fragment" style={{fontSize: '0.58em', marginTop: '0.5em', fontWeight: 'bold', color: '#e76f51'}}>
Any push that didn't touch a Markdown file looked identical. The one student who added a .md file got through.
</p>

<aside className="notes">
**Let the comment in the file do the work.** Read "You should almost definitely change this" out loud and pause. The template shipped a warning, in a file nobody had a reason to open after the assignment was created.

**Explain the check in plain terms for the mixed room.** For an assignment that doesn't allow empty submissions, Pawtograder hashes the student's files and compares the result with a hash of the starter code. It only looks at the files the patterns select, so that a changed lockfile or a stray build output doesn't count as work. If the patterns select the wrong files, the comparison is between two things that were never going to differ.

**Whose fault is it?** Nobody's, and say that. The template default was reasonable for the Java and Python courses it was written for, the staff had turned the autograder off and had no reason to open the file, and the platform did exactly what the config said. It's a systems failure: a default that is safe in one context and silently wrong in another, with no signal when it goes wrong. That framing is what a blameless postmortem looks like, and Thursday's postmortems use it.

**The fix was one commit to this file.** New pushes were accepted within a minute. The 40 already rejected stayed rejected, and restoring them took a reviewed script, run as a dry run first, then on one repository, then on the rest. Say the rule in one line, because Thursday needs it: **mitigate before you recover.** Stop new harm first, then repair what's already broken.

<aside className="notes">
**Point at the whiteboard for each row.** "Database" column: rows 2, 3, 4 and 6. "Code and config": row 5. "GitHub": row 7. "Logs": nothing. "Dashboards": nothing. Say the count, and compare it with what the room predicted in the warm-up.

<Slide>

## Why the Fix Was a Commit

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.55em', borderRadius: '8px', fontSize: '0.56em', textAlign: 'left', marginTop: '0.3em'}}>

**Definition.** **Infrastructure as code (IaC)** means the servers, containers, networks and settings a system runs on are **described in files under version control**, and a tool makes the running system match those files. You change the system by changing a file, not by clicking in a console.

</div>

<div style={{display: 'grid', gridTemplateColumns: '1fr 1fr', gap: '0.5em', fontSize: '0.5em', textAlign: 'left', marginTop: '0.5em'}}>

<div style={{backgroundColor: 'rgba(42,157,143,0.12)', padding: '0.5em', borderRadius: '8px'}}>

**In Pawtograder**

- A **Helm chart** (a template for Kubernetes resources) plus one values file per environment, such as `values-prod.yaml`
- Kubernetes itself: every service is a file describing what should run
- `pawtograder.yml` per assignment: **configuration as code**, the same idea for app settings

</div>

<div style={{backgroundColor: 'rgba(255,180,0,0.15)', padding: '0.5em', borderRadius: '8px'}}>

**What it buys you**

- **Review.** A change to production is a pull request
- **Reproduce.** Staging and previews come from the same files
- **Answer.** "What is running?" has a written answer

</div>

</div>

<aside className="notes">
**One slide, about two minutes. It's the first new term for half the room.** The contrast is the useful part: the alternative to IaC is a person logging into a server or a web console and changing a setting by hand. That works, once, and then nobody can tell what was changed, when, or why, and nobody can build a second copy.

**Name the tools only as examples, in one breath.** Terraform describes cloud resources, Helm and Kubernetes manifests describe what runs in a cluster. The Workspaces team will meet several of these in their own namespace this month.

**Configuration as code is the same idea one level up.** The file from Arc 1 is configuration as code: the grader settings for an assignment live in a git repository, and a webhook copies them into the database when you push. The fix for the incident was a commit, which means it was reviewable and it's in the history.

**The first and third "buys" are today's point.** Review: the fix was one commit, reviewable and in the history. Answer, in one sentence: `values-prod.yaml` pins the edge functions to the image tag `main-20260927-38db5c7b`, and `38db5c7b` is a commit, so I could read the exact code that rejected those pushes. Today's `main` might have a fix that wasn't deployed yet. The alternative is `tag: latest`, and then nobody can say which code is running. Sentry tags every error with the commit for the same reason (s06).

**Say plainly that the files were right about what was running.** Production ran exactly what they said. The webhook copied `pawtograder.yml` faithfully, and the pinned tag matched the deploy. The failure was a correct declaration of the wrong thing, which is why writing it down wasn't enough: nothing checked whether what was declared made sense for this course. Hold that for the postmortem.

> **Transition:** The files told us what was running. Here's where the rest of the evidence lives.

<Slide>

## Where the Evidence Lives

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.5em', borderRadius: '8px', fontSize: '0.52em', textAlign: 'left', marginTop: '0.2em'}}>

**Definition.** **Observability** is how well you can answer a *new* question about a running system from what it already records, without shipping new code. What it records is **telemetry**.

</div>

<div style={{fontSize: '0.44em', textAlign: 'left', marginTop: '0.4em'}}>

| | Answers | Pawtograder today |
|---|---|---|
| **Errors** | What broke, where, in which release, for whom | **Sentry → Bugsink**, every event tagged with the commit |
| **Logs** | What happened, line by line, in one process | Only what a pod still holds: **about two hours** |
| **Metrics** | How much, how often, how fast, over time | **Prometheus**, graphed in **Grafana**, with **37** alert rules |
| **Traces** | Where one request spent its time, across services | **Off** |

</div>

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.45em', borderRadius: '8px', fontSize: '0.5em', textAlign: 'left', marginTop: '0.4em'}}>

**Definition.** An **alert** is a rule over telemetry that notifies a person when it's true: "this number has been above that line for ten minutes."

</div>

<aside className="notes">
**Two definitions, and the first one needs care.** Observability is not a tool. It's a property of the system: can you answer a question you didn't plan for? Monitoring is the part you did plan for: the dashboards and alerts someone set up in advance. The incident was a question nobody planned for.

**Walk the table row by row, one sentence each, and connect each row to the incident.**
- Errors: they've seen Sentry in s06. A rejected submission isn't an exception, so nothing went to Sentry. The code was working as written.
- Logs: the most detailed record, and the one that disappears. With nowhere to send them (Loki, Elasticsearch, a cloud logging service), they vanish when the pod restarts or the buffer rolls over.
- Metrics: cheap, kept for weeks, and good for "is something changing?" They lose the details: a metric can tell you rejections went up; it can't tell you which student.
- Traces: off, because they cost storage and nobody has turned them on. s06 said this.

**Mention the database as a fifth source without adding a row.** Arc 1 showed most answers came from rows the software kept on purpose. That's telemetry too, in the widest sense, and it's the kind students will design into their own projects.

**Treat the table as a map for Thursday.** The column they need is the right one: where Pawtograder keeps each kind of evidence, and the one that's already gone after two hours. The Grafana and Sentry here are production's. Don't say anything about staging's monitoring; Thursday covers it.

## The Number Was Already There

<div style={{fontSize: '0.54em', textAlign: 'left', marginTop: '0.3em'}}>

Pawtograder already publishes this metric, every minute, per course:

## Blameless Postmortem: What Changes?

<div style={{backgroundColor: 'rgba(100,150,255,0.14)', padding: '0.45em', borderRadius: '8px', fontSize: '0.48em', textAlign: 'left', marginTop: '0.2em'}}>

</div>

<div style={{fontSize: '0.48em', textAlign: 'left', marginTop: '0.4em'}}>

**What let it happen:** a default that was right for Java and wrong for TypeScript · a file nobody had a reason to open · no signal to anyone for six days

<div className="fragment" style={{fontSize: '0.42em', textAlign: 'left', marginTop: '0.35em'}}>

| Action item | Who has to act |
|---|---|
| Page an operator when a course's pushes change only ignored files | An operator, who then emails the course staff |
| Tell the course staff directly, on their dashboard | The staff, who own the file |

<aside className="notes">
**This is where the talk ends, so give it the time.** About six minutes. Let the room argue. Thursday runs the whole incident loop live; today is about what we'd change.

**Say why blameless first, in two sentences.** The blame version of this postmortem is "the staff should have read the comment in the file." Its action item is "remind instructors to check `submissionFiles`", which needs a person to remember, every term, forever. The blameless version asks what made the mistake easy and the failure quiet, and those are things we can change in code.

**Take action items before revealing the table.** Expect "add an alert" first, because the last fifteen minutes were about metrics. For each one, ask the slide's question: who has to be awake? An alert pages an operator, who doesn't own the file, doesn't know the course, and has to email the people who do. That's a person added to the loop, at the worst time.

**Reveal the table and read it top to bottom.** Map the rows back to the three causes. "No signal" is the first three rows, and they get better as the message moves toward the person who can act on it: the student knows within seconds, and the staff can fix it the same day. "A file nobody had a reason to open" is the fourth: check it when someone is already looking at it. "A default right for Java" is the fifth: make the default come from the starter itself. The distinction from the last slide powers every one of the first three. Recording it was never only about the alert.

**Be honest about the trade.** The lower rows cost more to build and need product decisions: what should the student see, and should creation-time checks block or warn? An alert is cheap and fast to write, so it's often the first action item, and that's fine as a stopgap. It's the right final answer only when nothing lower on the table is possible. A postmortem whose only action item is an alert has usually stopped one question early.

**These rows are candidates, not commitments.** If any has shipped or been filed since Sep 29, say so and link it. Several would make good tickets.

**Connect forward.** Thursday's game day ends with a postmortem, and it has to name a prevention item. Push them toward the lowest row they can reach. The same question is the second step of the working session, about their own tickets.
