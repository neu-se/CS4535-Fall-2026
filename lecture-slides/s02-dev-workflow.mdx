## Path A: Frontend Against Staging

<div style={{fontSize: '0.7em', textAlign: 'left'}}>

```bash
git clone https://github.com/pawtograder/platform
cd platform
nvm install 22 && nvm use 22
npm install                       # ignore the deprecation wall
cp .env.local.staging .env.local  # nothing to fill in
npm run dev                       # https://localhost:3000
```

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,200,100,0.2)', padding: '0.5em', borderRadius: '8px', fontSize: '0.7em', marginTop: '0.8em', border: '2px solid rgba(255,180,0,0.5)'}}>

Your browser will warn you about the self-signed certificate. That's expected — click through. HTTPS is required for camera and microphone access in the help queue.

Sign in with **email and password**. OAuth on staging redirects to the deployed site, not your laptop.

</div>

<div style={{fontSize: '0.62em', marginTop: '0.6em'}}>

Every command on the next few slides also lives at [/docs/local-dev](/docs/local-dev).

</div>

<aside className="notes">
**If anyone doesn't have `nvm`, that's the first two minutes.** Install link is on the cheat sheet: https://github.com/nvm-sh/nvm#installing-and-updating. Node 22 matches CI.

**There is nothing to fill in, and say so explicitly.** `.env.local.staging` is tracked in git and holds only browser-facing values (Supabase URL, anon key, web URL). The secrets that pair with it live in an untracked `.env.local.staging.priv` and are staff-only; nothing on Path A needs them. The README still says "fill in your own values," which is now wrong — that's a free ticket for somebody in the new-contributor role.

**The email-and-password line saves an afternoon.** GoTrue's allow list on staging is `https://staging.pawtograder.net/*`, so a GitHub/Discord/Microsoft round trip bounces them to the deployed site and looks like a broken login on localhost.

**Point at the cheat sheet once, here.** Everything in Arc 2 is written down at `/docs/local-dev`, which means you can move faster than they can type.

> **Transition:** If your work needs the database, you need the whole stack.
</aside>

## Path B: The Full Local Stack

<div style={{fontSize: '0.56em', textAlign: 'left'}}>

```bash
# Docker must be running first
npx supabase start        # boots Postgres, Auth, Realtime, Storage
npx supabase db reset     # replays 400+ migrations, loads base data

# the CLI's key names are not the app's. Rename them on the way out:
npx supabase status -o env \
  --override-name api.url=NEXT_PUBLIC_SUPABASE_URL \
  --override-name auth.anon_key=NEXT_PUBLIC_SUPABASE_ANON_KEY \
  --override-name auth.service_role_key=SUPABASE_SERVICE_ROLE_KEY >> .env.local

npm run seed              # a test class with real logins
npm run dev

# only when you're exercising an edge function:
npx supabase functions serve --env-file .env.local
```

</div>

<div style={{backgroundColor: 'rgba(255,200,100,0.2)', padding: '0.4em', borderRadius: '8px', fontSize: '0.6em', marginTop: '0.4em', border: '2px solid rgba(255,180,0,0.5)'}}>

Then three by hand, which no command emits: `SUPABASE_URL` and `SUPABASE_ANON_KEY` (same values, without the `NEXT_PUBLIC_`), and `ENABLE_SIGNUPS=true`.

</div>

<div className="fragment" style={{fontSize: '0.68em', textAlign: 'left', marginTop: '0.6em'}}>

Then: app on `https://localhost:3000` · Studio on `localhost:54323` · captured mail on `localhost:54324`

</div>

<aside className="notes">
**Say why the `--override-name` block is on the slide at all.** A plain `npx supabase status -o env` prints `API_URL`, `ANON_KEY` and `SERVICE_ROLE_KEY`; the app reads `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. Paste the output as-is and nothing is configured, with no error anywhere that says so. Same text is at [/docs/local-dev](/docs/local-dev#path-b-the-full-local-stack), so nobody has to retype the flags from the screen.

**The amber box is the part that bites after they think they're done.** Each source key maps to exactly one name per run, so the `NEXT_PUBLIC_`-less duplicates cannot come out of the same command.

**`npm run seed` prints a wall of output.** Scroll up and search for "Login Credentials". Every seeded user's password is `change-it`.

**Studio on 54323 is underused and worth 30 seconds of demo.** Being able to look directly at the rows is how you debug an RLS problem, and Monday's session assumes they can.

**The mail catcher on 54324** is where magic-link and confirmation emails land locally. Students otherwise assume auth is broken.

**Say that `functions serve` is optional.** Browsing a seeded class doesn't touch an edge function, so nobody should be blocked on it today. It matters when they hit submissions, webhooks or the async workers, and the symptom is specific: those calls fail while everything else works.

**Two things from the cheat sheet worth naming out loud, because they change how Arc 4 goes:**
- `npx tsx scripts/GenerateMagicLink.ts <email>` prints a login URL for any user, no password needed. It's how you move between the four hunt roles in seconds.
- `FIXED_GRADER_EMAIL=you@northeastern.edu npm run seed` seeds *your* address into that role, so the grading pass happens as you. Same for `FIXED_INSTRUCTOR_EMAIL`, `FIXED_STUDENT_EMAIL`, `FIXED_ADMIN_EMAIL`.

**Also on the cheat sheet, not worth room time:** `npm run seed -- --help`, six templates from `micro` (30 students) to `large` (900), and `--date-range-start/-end` in days relative to now, which is how you manufacture a past-due assignment.

> **Transition:** One decision about how you run it, and then the gotchas.

## `dev` Is For Editing. Otherwise, Build.

<div style={{fontSize: '0.72em', textAlign: 'left'}}>

```bash
npm run dev              # compiles each route on first hit
npm run build && npm start   # a few minutes, then fast everywhere
```

</div>

<div style={{fontSize: '0.7em', textAlign: 'left', marginTop: '0.7em'}}>

`next dev` recompiles per route as you click. Fine while you're editing one page. Painful when you're exploring the app as four different roles, and fatal for a Playwright run.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,200,100,0.2)', padding: '0.5em', borderRadius: '8px', fontSize: '0.68em', marginTop: '0.7em', border: '2px solid rgba(255,180,0,0.5)'}}>

`NEXT_PUBLIC_*` is baked into the bundle at build time. Change it, delete `.next`, rebuild. And never run `dev` and `start` at the same time.

</div>

<aside className="notes">
**This is the slide that makes their hunt week bearable**, and nobody discovers it alone. Clicking through the instructor views on `next dev` feels like the product is slow. It isn't; the compiler is.

**Say the number:** the build wants ~8 GB of heap and takes a few minutes. That's a real cost on a small laptop, which is why it's a choice and not a rule.

**The fragment is the same fact as the E2E setup** they'll meet in s06: full-suite runs use a prod build on 3001 with `NEXT_PUBLIC_PAWTOGRADER_WEB_URL` exported *before* the build. Don't explain that today, just plant the build-time rule.

**If you're running long, this is the slide to cut** — it's on the cheat sheet, and Arc 2's work block matters more.

## The Three Gotchas

<div style={{fontSize: '0.62em', textAlign: 'left'}}>

1. **Your database is older than your checkout.** Symptoms all differ, cause is one: `column ... does not exist`, `Could not find the '...' column in the schema cache`, `no partition of relation "audit" found for row`. Fix: `npx supabase db reset`, then `npm run seed`. If `start` restored a stale volume, `npx supabase stop --no-backup` first.
2. **Wrong Supabase CLI.** The CLI is pinned to **2.105.0** in `package.json`. On older versions `db reset` dies with `must be owner of table objects`. Use `npx`, never a global install.
3. **You changed the schema and skipped `npm run client-local`.** The generated types still describe the old schema, so you get type errors that point anywhere except at your migration.

</div>

<div style={{fontSize: '0.62em', textAlign: 'left', marginTop: '0.5em'}}>

Schema change, in full: `npx supabase migration new <name>` · write the SQL · `npx supabase db reset` · `npm run client-local`

</div>

<p className="fragment" style={{fontSize: '0.72em', marginTop: '0.5em', fontWeight: 'bold', color: '#2a9d8f'}}>
All three are written down in <code>AGENTS.md</code>. Point your agent at that file.
</p>

<aside className="notes">
**Do not walk through all three in detail.** Put the slide up, say "screenshot this," and name the symptom for each so they can pattern-match later. The detail is in the repo and on the cheat sheet.

**Gotcha 1 is deliberately one gotcha and not three.** The stale-volume case, the schema-cache case, and the audit-partition case are the same fact wearing three error messages, and `db reset` fixes all of them. Teach the reflex: reset early, don't perform surgery on your local database.

**Gotcha 3 is the one that matters for column groups.** Everyone doing that assignment writes a migration, and the ones who skip `client-local` spend an evening on type errors in files they never touched. Say it now and again on 9/14.

**The fragment is the real lesson of the slide**, and it generalizes: the repo already documents its own traps, and the students who read `AGENTS.md` and `CLAUDE.md` before flailing get to the same place in a tenth of the time. This is also the first concrete instance of the course's AI posture — good context beats good prompting.

> **Transition:** Work block. Get to the checkpoint.
</aside>

## What CI Protects

<div style={{fontSize: '0.68em', textAlign: 'left'}}>

| Check | What it catches |
|---|---|
| `npm run lint` | ESLint violations, and unformatted code |
| Jest | Unit-level regressions |
| `npm run test:functions` | Deno tests for the edge functions |
| Playwright (~100 tests) | A user flow that stopped working |
| Argos | A page that changed appearance without anyone deciding to |
| Preview deploy | Your branch, running, at a URL commented on the PR |

</div>

<p className="fragment" style={{fontSize: '0.75em', marginTop: '0.8em', fontWeight: 'bold', color: '#e76f51'}}>
Run <code>npm run format</code> before you commit. CI rejects unformatted code, and that round trip is a wasted twenty minutes.
</p>

<p className="fragment" style={{fontSize: '0.7em', marginTop: '0.6em'}}>
Branch <strong>in the repo</strong>, not in a fork. The E2E lane won't run for a fork PR.
</p>

<aside className="notes">
**The Argos row is the interesting one** and worth naming as visual acceptance testing — most students have never seen it. It gets its own arc in s06.

**The preview-deploy row is the one that will surprise them:** every PR gets the whole stack stood up on the cluster at its own URL. That's how a reviewer looks at their work without checking out their branch, and it's the concrete payoff of Monday-after-next's IaC session.

**The first fragment is the single most useful sentence in this session.** Say it twice. It's the number one cause of a red first PR.

**The second fragment is why the push-access list matters.** The E2E workflow uses `pull_request_target` and gates on whether the head branch lives in `pawtograder/platform`, because that job executes PR code on the project's own runners. A fork PR gets lint and nothing else. Don't teach the security reasoning today, just the rule: branch in the repo, and get push access if you don't have it.

> **Transition:** CI is the cheap part of review. Humans are the expensive part.
</aside>

## What a Good PR Looks Like Here

<div style={{display: 'grid', gridTemplateColumns: '1fr 1fr', gap: '1em', fontSize: '0.68em', marginTop: '0.5em'}}>

<div style={{backgroundColor: 'rgba(42,157,143,0.12)', padding: '0.6em', borderRadius: '8px'}}>

**Gets merged**

- One concern, reviewable in one sitting
- Description says what changed and why
- Links the ticket
- Green CI before you ask for review
- Says how you tested it

</div>

<div style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.6em', borderRadius: '8px'}}>

**Sits for a week**

- Four unrelated changes in one branch
- Description is the branch name
- Red CI, awaiting review
- A formatting sweep mixed into a feature
- No indication anyone ran it

</div>

</div>

## The Other Half: Triage

<div style={{fontSize: '0.78em', textAlign: 'left'}}>

Two tickets filed, and two things somebody hasn't decided about, decided. Every triage reaches one of three verdicts:

1. **Still real.** The reproduction, who it affects, a size. It becomes claimable.
2. **No longer real.** Fixed, obsolete, or a false positive. Say how you know.
3. **Undecidable without something I don't have.** Name what you'd need and who has it.

</div>

<div className="fragment" style={{backgroundColor: 'rgba(255,200,100,0.2)', padding: '0.5em', borderRadius: '8px', fontSize: '0.72em', marginTop: '0.8em', border: '2px solid rgba(255,180,0,0.5)'}}>

The verdict earns nothing. The reasoning is the deliverable.

</div>

<aside className="notes">
**This half gets forgotten**, because filing is more fun than deciding. Say the split out loud: two filed, two triaged, and the triage is where the judgment is.

**Verdict 3 is a real answer, not a cop-out.** A student who writes "undecidable, I'd need to know whether phase 2 is scheduled and only the instructor knows" has done the assignment. Say so now or you'll get four of them apologizing.

**The trap worth naming:** the same `TODO` text appears in six migration files. That's one issue, not six. And a suppression with a written justification above it is somebody's decision, not their ticket.

> **Transition:** Second work block. Get wired up, then claim.
</aside>

## Session Capture: Install Entire

<p style={{fontSize: '0.72em', textAlign: 'left'}}>
Required on every repo you work in this semester. One install, one enable, then it rides along on <code>git push</code>.
</p>

<div style={{fontSize: '0.58em', textAlign: 'left'}}>

```bash
# macOS / Linux
brew tap entireio/tap && brew trust entireio/tap
brew install --cask entire
# no Homebrew: curl -fsSL https://entire.io/install.sh | bash
```

```powershell
# Windows, PowerShell 5.1 or later
irm https://entire.io/install.ps1 | iex
```

```bash
cd platform
entire enable --local \
  --checkpoint-remote github:neu-cs4535/fa26-entire-checkpoints
entire status   # checkpoint destination must be the corpus repo
```

</div>

<div className="fragment" style={{backgroundColor: 'rgba(100,150,255,0.12)', padding: '0.5em', borderRadius: '8px', fontSize: '0.68em', marginTop: '0.6em'}}>

It hooks whichever agent you use and stores each session beside the commit it produced. Transcripts go to a private course repo, never to `pawtograder/platform`. Who reads them, and how to opt out of the research half: [syllabus](/syllabus#what-we-keep-from-your-sessions).

</div>

<div className="fragment" style={{backgroundColor: 'rgba(42,157,143,0.12)', padding: '0.5em', borderRadius: '8px', fontSize: '0.66em', marginTop: '0.5em'}}>

**Already have the stack running?** Give your agent one small task, commit it, then read back what got captured: `entire checkpoint list`, then `entire checkpoint explain <id>`.

</div>

<aside className="notes">
**Confirm every student's GitHub account has write access to `neu-cs4535/fa26-entire-checkpoints` before class.** A student whose checkpoint push is rejected gets a warning on `git push`, not a failure, so a broken corpus is silent and you find out in October.

**Why `--local`:** it writes the setting to `.entire/settings.local.json`, which is gitignored, instead of `.entire/settings.json`, which is committed. Students branch in `pawtograder/platform` itself, so without `--local` their first PR carries a config change nobody asked for.

**Why `--checkpoint-remote` at all, in one sentence if asked:** checkpoints are git refs, so by default they ride to the repo you push code to, and that repo is public. The flag sends them somewhere private instead. Don't teach the ref layout today.

**`entire enable` prompts for which agent to hook.** Claude Code, Codex, Copilot CLI, Cursor, Gemini, opencode and Pi are all on the list, so nobody has to switch tools. They can add a second one later with `entire agent add <name>`.

**The line that has to land: `entire status` is the checkpoint.** It prints the checkpoint destination and how many are unpushed. If the destination reads `pawtograder/platform`, the enable didn't take and their transcripts are headed somewhere public. Ask for hands on the destination line, not on "did it install".

**The green box is the in-class stretch for the students who are already running.** A rename or a one-line test is enough to produce a checkpoint. `entire checkpoint explain` is the slide that sells the tool, because seeing your own prompt and diff paired is the moment it stops sounding like surveillance and starts looking like a tool. Demo it yourself if the room is thin on working stacks.

**Say the credential rule here, briefly.** Redaction is best-effort and a hardcoded secret in the working tree can ride through in a snapshot. If something sensitive lands in a session, tell us and we purge and rotate.

> **Transition:** Second work block. Get wired up, then claim.
</aside>

## The 30-Minute Rule

<p style={{fontSize: '0.85em'}}>
Thirty minutes of no progress on the same problem, and you owe the team a question.
</p>

<div className="fragment" style={{fontSize: '0.75em', textAlign: 'left', marginTop: '0.8em'}}>

Not because struggling is bad — struggling is where the learning is. But because **silent** struggling is invisible to everyone who could have unblocked you in ninety seconds.

</div>

<p className="fragment" style={{fontSize: '0.8em', marginTop: '0.8em', fontWeight: 'bold', color: '#e76f51'}}>
The failure mode isn't asking too early. It's a student who says nothing for eight days.
</p>

<aside className="notes">
**This is a culture-setting slide and it needs your delivery, not the words on it.** Students arrive from courses where asking is a penalty, and in a studio course that instinct is genuinely destructive.

**Name the standup connection:** "blocked" with a specific ask is the most valuable line anyone posts on a Monday. It gets its own objective in s11.

## How to Ask

<div style={{fontSize: '0.7em', textAlign: 'left'}}>

**Four lines. That's the whole template.**

1. What I'm trying to do
2. What I did
3. What I expected, and what happened instead — **paste the actual error**
4. What I already ruled out

</div>

<div className="fragment" style={{backgroundColor: 'rgba(231,111,81,0.15)', padding: '0.5em', borderRadius: '8px', fontSize: '0.7em', marginTop: '0.8em'}}>

Not: "supabase isn't working, any ideas?"

</div>

<div className="fragment" style={{backgroundColor: 'rgba(42,157,143,0.12)', padding: '0.5em', borderRadius: '8px', fontSize: '0.7em', marginTop: '0.5em'}}>

Instead: "Running `db reset` to get the seeded class. It fails at migration `2026…` with `must be owner of table objects`. I checked I'm on the pinned CLI via `npx`. Full log in the thread."

</div>

<aside className="notes">
**The two example fragments do all the work here.** Read both out loud. The contrast teaches faster than the numbered list above them.

**Say the honest thing about why this matters:** a well-formed question gets answered in minutes because it's answerable. A vague one sits because answering it means interviewing you first.

**The same template makes a good ticket, a good PR description, and a good standup post.** It's one skill wearing three hats — worth naming.

> **Transition:** And here's where each kind of question goes.
