Grading 20 submissions in a row

A walkthrough of the grader-facing submission view as it ships on staging (146759be). It covers three roles: a grader with assigned reviews, a grader with nothing assigned, and an instructor. It ends with a proposed scope for one larger PR.

Captured 2026-10-03 on a fresh local stack (433/433 migrations, production build) Seeded: 6 students, 2 graders, 1 instructor; one code assignment and one survey-only (no_submission) assignment
1 confirmed bugThe Review Task box shows the assignee's profile UUID. Anyone else viewing the submission sees no assignee at all.

The bug: "Assigned to: <uuid>"

Replacing the UUID with a name is a one-line change: <PersonName uid=… showAvatar={false} />. That component is already imported in the file and already used by the review toolbar. The one-line fix only fixes the case where the line matters least, though:

  • Assigned grader. The box only renders for the active review assignment, which useMyReviewAssignments filters to the viewer's own. So the name it shows is always the viewer's own.
  • Another grader, or an instructor. The box doesn't render at all. If an instructor opens a link with someone else's ?review_assignment_id, the param is stripped. Nothing on the page says the submission belongs to Gary (screenshot below).
  • Assignment dashboard. The "Grader" column is gradername, which is who completed the review (completerprofile.name in the submissions view). It stays blank until the review is done. The dashboard has no column for who is assigned.

The fix for all three: load every review assignment on the submission for staff viewers, and render a line like "Assigned to Gary Grader (you) · due Oct 5", "Assigned to Gary Grader · due Oct 5", or "Not assigned". The same source can drive an "Assigned grader" column on the dashboard.

Proposed scope for the PR

This is grouped so the first tier can ship on its own if the PR gets too big. Every item in the first tier removes a per-submission click or fixes wrong information.

Tier 1: the 20-in-a-row loop

  1. Assignee shown to every staff viewer, by name. Show "(you)", another grader's name, or "Not assigned", with due date and status. Covers the bug and both flows (assigned and unassigned).
  2. Remember the sub-tab per assignment. Save the last tab used for that assignment, and have every cross-submission link use it: Next Incomplete, the dropdown, the selector, Complete + Next, and the table rows. If the next submission doesn't have that tab, fall back to the default.
  3. Survey becomes the default tab on no_submission assignments that have a linked survey, both for the first visit and for the canonicalizing redirect.
  4. One completion control with "Complete + Next". Available on the review-assignment button too, so part-scoped graders get it.
  5. Previous / Next in the toolbar, using the same order as the "Assigned to me" table.

Tier 2: less scrolling, clearer labels

  • Move the rubric to the top of the sidebar. Put the review task in the toolbar banner (one due date), and collapse automated checks by default.
  • For staff, rename the Grade tab to something like "Student view", or make it the editable rubric, consistent with no-submission assignments.
  • Keyboard shortcuts: next/previous submission, complete + next, and switching tabs (? help already exists).
  • Add an "Assigned grader" column on the assignment dashboard, next to the completer column.

Out of scope: separate tickets

  • Fix the staff /grade/… route's broken links and Survey tab.
  • Make "Assigned to me" rows real links.
  • Remove the review_assignment_id redirect hop.

Questions to settle before building

Where should tab memory live?

Options are localStorage per (assignment, user), or the URL (carry the current sub-page on every navigation link). The URL is simpler and survives a shared link. localStorage also covers "come back tomorrow". I'd do both: the URL first, localStorage as the fallback.

Should the memory be per assignment or global?

Per assignment avoids carrying "Survey" onto a code assignment that has no survey tab. A global setting would be wrong on mixed assignment types.

Should completing auto-advance?

One option is to make "Complete + Next" the primary action and "Complete" secondary. The other is a per-user preference.

What should "Next" follow?

The table order (due date, then name), submission ID as today, or a fixed order chosen when grading starts?

Should an unassigned grader be able to complete someone else's review?

Today Grace gets a working "Complete Review" on Gary's submission. Should showing the assignee come with a warning, or with a restriction?

Method and caveats

I took the screenshots with a temporary Playwright script against a production build on localhost:3001, with the e2e harness's visual-test masking turned off. The masking replaces the "Assigned to" line with a placeholder, which is why existing visual tests never caught the UUID. The survey-only submissions were seeded with the pre-baked submission helper, so they show autograder checks that a real manual submission wouldn't have. The Grade/Survey tab behaviour doesn't depend on that. Code references point to staging at 146759be.
